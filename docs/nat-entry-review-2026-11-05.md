# NAT IPv4 / 线路 IPv6 分路修复与升级

范围：Panel `790a06b`、`8bc5055` 与 Script `f2dc830`、`cb7f506` 引入的公开入口功能及关联的授权、迁移、监控、交互。修复版本为 Panel / Agent **1.3.11**、Script **2.7.16**，配合 [定制 Mihomo 最新构建](https://github.com/Chen017/mihomo/releases/latest)。服务端 Xray-core 保持 **26.3.27**。

## 目标链路

客户端 IPv4 上传先连接 NAT 的公开随机加密入口，再从 NAT 访问线路机 XHTTP；客户端 IPv6 下载直接连接线路机。线路机继续通过原有 VLESS RAW + Vision + Encryption 互联使用 NAT 落地出口。反向的 IPv6 上传 / NAT IPv4 下载同样支持。

公开入口继续使用 `mlkem768x25519plus.random.0rtt` 与原有 padding。移除的是公开入口的 Vision flow；线路至落地的 Vision 保留。客户端仅关闭公开入口的 TFO，MPTCP 保留。

## 已确认的问题与修复

| 问题 | 影响 | 修复与验证 |
| --- | --- | --- |
| XHTTP 下载继承上传的前置代理 | IPv6 下载也经过 NAT，无法实现预期分路 | 新核心支持 `download-settings.dialer-proxy`；省略继承、空字符串 / DIRECT 直连、名称指定独立代理；真实拨号测试确认两种方向 |
| 前置代理只在全局节点中查找 | HTTP / inline Provider 内同级 NAT 节点无法被引用 | 全局优先，再查所属 Provider；刷新后重新查找，拒绝循环与跨 Provider 猜测 |
| 旧部署仍有公开入口 Vision flow | 新建配置修了，旧配置未迁移；完整 TLS 流量仍失败 | Script schema 4 与 Panel 编译都移除公开入口所有客户端的 flow；真实 Xray 复现旧错误并验证迁移恢复 |
| NAT 公开入口客户端启用 TFO | 实际线路上普通 HTTPS 超时 | 同一地址、同一入口对比：关闭入口 TFO 后 HTTPS 成功；订阅和脚本共用正确导出，保留 MPTCP |
| 零 RTT 在部分提前断开 / 认证失败后仍复用旧票据 | 重启或失效时可能重复使用坏缓存 | 首个认证响应前的读取失败使对应票据过期；旧连接不能清掉更新的票据。测试确认首次获取、后续零 RTT、失效后重新握手再零 RTT |
| 关联入口使用共享脚本 UUID，缺少跨节点授权同步 | 设备撤销 / UUID 轮换无法完整隔离入口；只部署线路就可能发布不可用链路 | 托管关联入口按源节点、设备、出口派生独立 UUID；同步到 NAT，等待两端成功后发布；撤销删除入口权限。直连托管 NAT 也必须先部署设备 UUID，禁止回退到共享凭据 |
| 公开入口仍按纯落地排除国内检测 | 兼作公网入口时缺少国内连通证据 | Agent 检测协议 4 按运行配置区分：公开入口检测国内与海外，纯互联落地仅海外。角色变化后重新读取，旧 Agent 提示升级 |
| 新入口藏在高级参数，生成结果要手动读取 | 操作步骤多，易保存不完整草稿 | 独立入口卡片、开关、映射关系、生成进度与就绪状态；按具体任务自动回填，保持保存 / 预览 / 部署原流程 |
| 关闭入口后残留未填写或无效参数；缺密钥时回退互联参数 | 关闭也不能保存，或生成不匹配配置 | 关闭先清除入口专属字段；开启校验独立密钥、UUID、内外端口冲突；CLI 端口修改要求完整凭据 |
| NAT 入口复用互联地址族；链式配置导出单条 URI | IPv6 互联误用于 IPv4 入口；分享链接丢失前置代理 | 关联入口单独同步 IPv4 地址；链式配置明确要求完整 Mihomo YAML / Provider，单条 URI 仅用于可独立表示的连接 |

外部手动导入的落地未接入面板时，脚本共享 UUID 仍由操作者管理；只有托管关联节点可以自动同步按设备授权。为维持已有手动客户端，不自动删除脚本原始凭据。

国内三网检测是 **VPS 向外发起连接**，不能证明中国客户端到 NAT 入口的 IP / 端口未被阻断。TCP 探测也不能替代完整代理流量测试。

## 零 RTT 的恢复边界

首次连接需要完整握手获取票据，后续连接走零 RTT。服务端重启丢失票据后，首个旧票据请求可能失败一次；下一连接重新获取票据后继续零 RTT。客户端不会自动重放已发送的应用数据。此次没有把入口默认改为 1-RTT。

## 升级顺序

1. 从 Fork 的最新 Release 下载新 Mihomo，按 [核心更换说明](https://github.com/Chen017/mihomo/blob/codex/window-builds/WINDOW-CORE.md) 替换 Clash Verge 管理的核心。当前选择 alpha 核心时对应 `verge-mihomo-alpha.exe`，选择稳定核心时对应 `verge-mihomo.exe`。保留备份；服务模式使用 Clash Verge 的服务管理更新副本，核对实际运行版本，不能只看下载文件版本。
2. 控制中心运行 `xray-panel panel update --version 1.3.11`；线路机和 NAT 落地分别运行 `xray-panel agent update --version 1.3.11`。
3. 两台机器的 Script 更新到 2.7.16，可在面板执行「更新脚本」，或进入 Script 的「杂项管理 → 更新 → 更新脚本」。无需升级或重装 Xray-core。
4. 导入并核对 NAT 当前配置，在「线路 / 落地 → 公开 IPv4 入口」保留原映射端口、独立密钥，保存并部署。在线路机选择面板内关联的 NAT 落地，保留原互联设置，再核对并部署线路。等待关联授权同步任务成功；不要从未部署的草稿复制客户端配置。
5. Clash 手动刷新 `xray` Provider。先测 NAT 入口，再测分离节点；连续测试和完整 HTTP/HTTPS 加载都应验证。升级后仍失败时采集该时间点的两端 Xray 日志和客户端日志，继续区分入口、Reality、下载和互联出口。

Panel 更新不会代替节点 Agent 更新。后台网络检测需在设置中启用；不会因打开入口开关而自动启用 Telegram 通知。

## 1.3.12 追加修复

- NAT 前置入口的自定义名称会用于节点本身及所有上传/下载拨号引用，可以保存、修改或清空；重名校验包括依赖的前置入口。
- 线路机每个落地卡片新增“通过此落地的 NAT IPv4 过墙”开关。关闭后恢复线路机原双栈分离，保留出口互联及开关偏好；关联同步不会重新强行打开。保存并部署后生效。
- NAT 公开入口的 TLS 嗅探会把内层 Reality SNI 用于路由。若 SNI 在 geosite:cn 中，原阻断规则可能误拦线路互联。本地规则库确认本次 IPv4 SNI 所属域命中 cn；真实 Xray 测试复现该阻断，并验证恢复。
- 编译器为托管关联线路生成按设备用户、公开入口 inbound、线路 IP、TCP 入站端口限定的直连规则，置于国家/域名阻断之前、私网拒绝之后。其他流量仍受原规则约束。撤销、关闭过墙或解除关联会移除该规则；旧配置的授权相同但路由缺失时仍会自动同步。
- 生产故障仍需在 NAT 部署该修复后复测，不能以本地复现代替生产日志确认。手动导入且未托管关联的落地需单独维护互联例外。
